# Figma MCP レスポンシブ実装ガイド

Oct 21, 2026 · @Akito Okubo

## 目的と使い方

Auto Layoutのないデザイナー作成データ（PC/SP）を、Figma MCP経由で高精度にレスポンシブ実装するための手順とルールをまとめたガイドです。人が読む手順書であると同時に、AIに毎回読ませる指示書として使います。

AIへの参照のさせ方は、作業環境ごとに次のとおりです。

| 作業環境 | 参照のさせ方 |
| --- | --- |
| Claude Code | このドキュメントをMarkdownで書き出し、リポジトリの `CLAUDE.md` または `.claude/rules/` に配置する |
| Cursor等のエディタ | Markdownで書き出し、プロジェクトルール（rulesファイル）に配置する |
| claude.aiのProject | Markdownで書き出し、プロジェクトナレッジに追加する |

- このドキュメントを正本とし、ルールを更新したら書き出し直して配置ファイルを差し替える
- 案件ごとに異なる情報（ブレークポイント、テンプレートのパス等）は、案件側のルールファイルに分けて書く

## 共通ルール

Figmaの生成コードは使わず、Figmaを「仕様の読み取り元」として扱います。Auto Layoutのないフレームでは生成コードが絶対配置になるため、メタデータとスクリーンショットからレイアウト意図を再構成します。

1. **セクション単位で処理する**：ページ全体を一度に渡さない。セクションごとに `get_metadata` / `get_screenshot` / `get_variable_defs` を取得し、1セクションずつ実装する。
2. **中間仕様を挟む**：「メタデータ＋スクショ → レイアウト仕様 → コード」の2段階で進める。仕様には要素順、グリッド列数、揃え、余白、フォントサイズをブレークポイント別に書く。
3. **座標からレイアウトを推論する**：x位置が等間隔に並ぶ要素はグリッド、y位置が揃う要素は横並び、と明示的に判断させる。絶対配置（`position: absolute` での再現）は禁止。
4. **既存テンプレートを優先する**：SP専用LPで使っているテンプレートのコンポーネントに当てはまるものは、新規に書かずそれを使う。
5. **検証ループを回す**：Playwrightで375px・1440px幅のスクショを撮り、Figmaの `get_screenshot` と比較して差分を修正する。2〜3周を目安にする。

デザイナーへのお願いは次の3点に限定し、Auto Layoutは求めません。

- セクションごとにフレームを分ける
- PCとSPで同じセクション名を付ける（例：`03_feature`）
- アートボード幅を固定する（PC 1440px / SP 375px）

## パターン1：PC＋SPデザインからレスポンシブ実装

PCとSPのセクションを対応付け、差分表を作ってから、モバイルファーストで実装します。

1. **セクションの対応付け**：同名フレームでPCとSPをペアにする。命名がない場合は、テキスト内容の一致を主キーにしてマッチングする。
2. **差分表の作成**：要素ごとに、PCとSPそれぞれの並び順、カラム数、フォントサイズ、余白、表示/非表示を表にする。
3. **実装方針の割り当て**：差分の種類ごとに下表の書き方で実装する。
4. **検証**：375px・1440pxに加え、768px付近でも崩れがないか確認する。

| 差分の種類 | 実装方針 |
| --- | --- |
| 並び順が変わる | `order` または `grid-template-areas` |
| 片方にしかない要素 | 表示切替ユーティリティ |
| 数値の差（フォント・余白） | 375〜1440pxの間で `clamp()` による線形補間 |
| カラム数の変化 | ブレークポイントでgrid定義を切替 |
| 画像の切り抜きが違う | `<picture>` で出し分け、または `object-position` |

デザインにない中間幅（タブレット等）は `clamp()` の補間で対応し、それでも崩れる箇所だけブレークポイントを追加します。

## パターン2：PCデザインのみからSPを生成

SP化はデザイン判断なので、AIの自由裁量にせず、下の変換ルールブックを適用させます。生成したSPは必ず人が確認します。

1. **セクション分類**：PCの各セクションを種別（ヒーロー、特徴グリッド、CTA、FAQ、比較表、フォーム等）に分類する。
2. **テンプレートへのマッピング**：種別ごとに、既存SPテンプレートのどのコンポーネントに落とすかを決める。
3. **ルール適用**：下表の変換ルールで実装する。ルールにないケースは、判断理由を中間仕様に書いて人の確認を待つ。
4. **確認とルールへの還元**：プレビューURLでデザイナーかディレクターに確認してもらい、指摘をこのルールブックに追記する。

| PCのレイアウト | SPでの変換ルール |
| --- | --- |
| 画像＋テキストの横並び | 画像を上、テキストを下に縦積み |
| 3〜4カラムのカード | 1カラム。カードが小さい場合は2カラム |
| グローバルナビ | ハンバーガーメニュー |
| 表 | 横スクロール。列が少なければ縦積みカード |
| 見出し・本文のフォントサイズ | フォントサイズ対応表に従う（要作成） |
| セクション上下余白 | PC値に縮小率を掛ける（要決定） |
| 背景画像 | 主被写体が残るよう `object-position` を指定 |

フォントサイズ対応表と余白の縮小率は、パターン1の過去案件（PC/SPのペア）から実測値を抽出して埋めます。

## AIへの指示テンプレート

作業開始時は、下のプロンプトの `{ }` を埋めて渡します。中間仕様は下のフォーマットで出力させ、人が確認してからコード化に進めます。

**プロンプト雛形（パターン1）**

```markdown
Figma MCPレスポンシブ実装ガイドに従って実装してください。

- PCフレーム: {PCのFigma URL}
- SPフレーム: {SPのFigma URL}
- 対象セクション: {例: 03_feature}
- 使用テンプレート: {テンプレートのパス}

手順:
1. PC/SPそれぞれ get_metadata と get_screenshot を取得
2. 中間仕様フォーマットで差分表を出力し、ここで一度止まる
3. 承認後、モバイルファーストで実装
4. 375px/1440pxのスクショを撮り、Figmaと比較して修正
```

パターン2では、SPフレームの行を削除し、手順2を「セクション種別とSPへの変換方針を中間仕様に出力」に置き換えます。

**中間仕様フォーマット**

```markdown
## セクション: {セクション名}（種別: {ヒーロー/特徴グリッド等}）
使用コンポーネント: {テンプレート内のコンポーネント名 / 新規}

| 要素 | PC | SP | 実装方針 |
| --- | --- | --- | --- |
| 見出し | 48px / 中央揃え | 28px / 中央揃え | clamp(28px, …, 48px) |
| カード | 3カラム / gap 32px | 1カラム / gap 16px | grid切替 @768px |

判断が必要な点:
- {ルールにないケースと、その判断理由}
```

## MCP利用環境の前提

このワークフローはMCPを1案件で数十回呼び出すため、Professional以上のプランのDevシートかFullシートが必要です（2026年6月時点の情報。最新はFigma公式ヘルプで確認）。

| プラン・シート | MCPの利用 |
| --- | --- |
| Starterプラン、またはView/Collabシート | ツール呼び出しが月6回程度に制限され、実用不可 |
| Professional以上のDevシート / Fullシート | 月間回数の制限なし（分単位のレート制限あり） |

- 元データをコピーして別チームで扱う場合、デザイナーの修正が反映されないため、修正のたびに再コピーが必要
- 元チームのライブラリにアクセスできないと、コンポーネントや変数の参照が切れ、`get_variable_defs` でトークンが取れないことがある
- 会社・クライアントのデータを個人契約アカウントへ移す場合は、社内規程とNDAを事前に確認する

## 導入の進め方

パターン1から着手し、そこで得た変換傾向をパターン2のルールブックに流用します。

- [ ] このガイドをMarkdownで書き出し、作業環境のルールファイルに配置する
- [ ] デザイナーにセクション命名と幅固定の3点をお願いする
- [ ] 過去案件1〜2件でパターン1を試し、スクショ比較で精度を測る
- [ ] 過去案件のPC/SPペアから、フォントサイズ対応表と余白の縮小率を抽出してパターン2の表を埋める
- [ ] パターン2を1件試し、確認での指摘をルールブックに追記する
